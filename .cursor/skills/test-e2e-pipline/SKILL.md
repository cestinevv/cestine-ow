# Test E2E Pipline

## 与 `webapp-testing` 自动衔接（强制）

本技能作为 **上层编排技能**。当任务涉及 UI 层面的集成测试落地（编写/更新可执行用例）时，必须自动衔接并执行 `@.agents/skills/webapp-testing/SKILL.md`，不得只停留在测试计划或断言清单。在本仓库中，该衔接仅用于吸收方法论与步骤约束，不得切换到 Python 执行链路。

### 衔接触发条件

满足任一条件即触发自动衔接：

- 用户要求“创建/补充/修复 UI 集成测试用例”。
- 用户要求“基于联调结果落地 E2E 用例代码”。
- 用户要求“验证页面交互链路并产出可执行测试脚本”。

### 衔接执行顺序（固定）

1. 先按本技能完成范围收敛：模块边界、最小 E2E 集（入口/主操作/结果可复现）、UI + Network 双层断言。
2. 立即加载并遵循 `webapp-testing`：采用其推荐的 Playwright 落地方式（含服务管理、侦察后操作、等待策略）。
3. 生成并提交真实测试代码（而非仅建议）。
4. 运行对应 e2e 子集并给出可审计结果。

### 实现约束（避免偏离）

- 必须使用仓库原生 Playwright 测试体系（既有目录、`playwright.config.*`、`test:e2e` 相关命令）。
- 禁止在本技能执行链路中落地 `Python + with_server.py` 方案；`webapp-testing` 在本仓库仅用于补充方法论（如侦察后操作、等待策略、选择器实践），不改变执行栈。
- 禁止出现“只写流程文档，不落地测试代码”的结果。

## 适用场景

当用户给出以下任意上下文时，触发本技能：

- 某个联调模块刚完成，需要验证端到端可用性。
- 既有模块发生接口、路由、交互、状态管理变更，需要快速回归。
- 需要把“手点验证”沉淀为可重复执行的 E2E 测试。
- 要求为后续迭代建立质量门禁（变更后必须运行 e2e）。

## 目标

将“联调完成”升级为“可回归、可复现、可门禁”的质量闭环，并满足：

- E2E 用例覆盖核心业务主路径（而非细枝末节）。
- 断言同时覆盖 UI 可见结果与关键网络行为（请求/响应状态）。
- 用例组织可迁移，不绑定单一业务命名或目录结构。
- 每次模块变更后可快速执行，输出可审计证据。

## 执行流程

### 1) 先做项目适配（迁移性关键）

先识别本仓库的等价实现，并建立映射表：

- 测试运行器：Playwright/Cypress/Webdriver 或等价方案。
- 测试入口命令：`test:e2e`、`e2e` 子集命令或 CI 里的等价命令。
- 页面模型组织：Page Object/Screenplay/直接 locator 风格。
- 环境注入方式：`.env`、`process.env`、CI secrets。

产出一段映射：`本技能术语 -> 本项目真实实现`，后续全程按映射执行。

### 2) 定义“E2E 最小集”

围绕联调模块，先提炼 3 类最小关键路径：

- **入口可达**：路由可进入，首屏关键区块可见。
- **主操作可达成**：至少 1 条 create/update/delete 或等价核心动作可成功。
- **结果可复现**：刷新或重新进入后，关键结果仍可被读取到。

禁止把完整回归套件当最小 E2E 套件；优先“快、稳、关键”。

### 3) 构建双层断言（UI + Network）

每个关键步骤至少包含一条：

- UI 断言：标题、列表项、按钮状态、错误提示、空态等用户可见结果。
- Network 断言：关键请求已发出，方法与状态码符合预期（2xx/4xx 等）。

避免仅断言“接口成功”却不看页面，也避免只看页面不验证关键请求链路。

### 4) 固化测试结构与命名

优先复用项目现有测试组织约定：

- 目录按业务域分组（例如 `tests/e2e/<module>/`）。
- 公共动作下沉到 page object 或 helper，减少重复 locator。
- 用例命名使用“行为 + 预期”的可读描述，避免实现细节命名。
- 测试场景描述（`test('...')` / `test.describe('...')`）统一使用中文，禁止中英文混写或纯英文标题。

新增测试时优先补“主路径与高风险断点”，不是平均撒网。

### 5) 处理不稳定因素（提高可维护性）

必须显式处理：

- 数据隔离：测试数据唯一化（时间戳/随机后缀）避免相互污染。
- 等待策略：优先等待可观察状态（元素可见/隐藏、响应完成），禁止盲等固定秒数。
- 环境差异：本地与 CI 的 baseURL、API URL、鉴权开关有默认兜底。

如果模块依赖外部服务不稳定，需提供 mock/测试环境前置说明。

### 6) 变更后门禁策略（本技能核心）

只要联调模块出现以下任意变更，必须运行对应 e2e：

- 路由入口变更（路径、参数、重定向逻辑）。
- 接口契约变更（字段、状态码、错误结构）。
- 核心交互变更（主按钮、表单提交流程、状态切换）。
- 数据渲染策略变更（空态、错误态、加载态、持久化行为）。

最小执行门槛：至少运行该模块 e2e 子集；若影响跨模块共享能力，再追加全量 `test:e2e`（按项目脚本）。

## 输出格式

完成任务时，回复必须包含：

1. 本次新增/更新的测试文件列表（不得为空）及职责说明。
2. E2E 场景清单（入口、主操作、结果可复现分别对应哪些用例）。
3. 双层断言说明（每条用例的 UI 断言 + Network 断言要点）。
4. 本地验证结果（至少 2 条真实命令与结果摘要）。
5. 门禁建议（模块变更触发哪些 e2e 命令）。

## 强制执行门禁（必须同时满足）

- 必须有真实测试代码改动，且至少覆盖 1 条主路径用例。
- 必须执行仓库可用验证命令（至少 `test:e2e` 子集或等价命令）。
- 必须给出证据矩阵：`断言目标 -> 测试文件 -> 关键符号/步骤`。
- 必须说明本次是否衔接了 `webapp-testing`，并明确落地方式为仓库原生 Playwright。
- 若用户未明确要求“仅评审”，禁止只写建议不落地测试代码。

## 验收清单

- 是否覆盖入口可达、主操作成功、结果可复现三类 E2E 路径。
- 是否每条关键路径都包含 UI 与 Network 两类断言。
- 是否复用项目既有测试组织方式（目录、page object、命名）。
- 是否避免固定时长硬等待，采用可观察条件等待。
- 是否提供了模块变更后的 e2e 执行建议与命令。

## 失败信号（出现任一项需返工）

- 只有 happy path，无错误态/空态相关最小覆盖。
- 仅有 UI 截图式断言，缺少关键请求链路验证。
- 用例强依赖脏数据，重复执行不稳定。
- 变更后未运行 e2e 或无可审计执行证据。
- 只交付文档说明，未新增/更新可执行测试代码。
